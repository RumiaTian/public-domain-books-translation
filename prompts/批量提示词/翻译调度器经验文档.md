# 翻译调度器经验文档

> 建立：2026-10-24（v4.2 架构定稿后）。读者：本人，以及任何被要求"检查昨晚跑批情况"的新审计会话。
> 性质：运维知识库 + 踩坑实录 + 排查 SOP。机制细节以 `mcp/translate_mcp.py` 与提示词正本（`prompts/批量提示词/2_定时轮次翻译提示词.md`）为准，本文记录**为什么这样设计**和**出过什么事**。

---

## 一、系统现状速览

目标：`翻译项目/` 648 本公版书全自动中译。**每天 4 个额度窗口全部跑满**——当前书跑完就开新书，唯一的窗口终结者是系统（额度耗尽 / 内容拦截），worker 永不自主收尾。

架构自上而下：

```
Cron 定时任务 ×4（各绑定独立的创建会话，轮次串行注入）
 → 调度会话（瘦分发器：只派 worker / 管槽位 / 收尾 git，~3.5K tokens/firing）
   → worker ×2（general-purpose 后台子代理，一次性上下文，每章 ~25K tokens）
     → translate-mcp 工具流（batch_begin → claim_task → context_pack → get_blocks → 直译 → submit_translation）
       → 状态落盘（项目 CSV / 认领锁 / 双语译文 / 拦截清单 / 活动日志）
         → git：开局 pull 同步 Mac 进度，收尾只提交 翻译项目/ + mcp/ 并 push（根看板归 Mac 端）
```

在跑任务（提示词均已同步 v4.2）：

| automation ID | cron | batch_id | 备注 |
| :--- | :--- | :--- | :--- |
| automation-11feab52 | `0 18 * * *` | 1 | PM1800。前身 v1 毒会话已删，现任务在新会话（898152de）重建 |
| automation-e73c5ce9 | `5 21 * * *` | 2 | PM2105 |
| automation-64d73759 | `10 2 * * *` | 1 | 2:10 窗口，"额度充足却 2 分钟暴毙"事故现场（§4.4） |
| automation-bc5a15a5 | `15 7 * * *` | 2 | AM0715。**绑定会话服务器为 10-23 前旧代码（§4.10 僵尸），待新会话重建** |

四窗口映射 **1/2/1/2** 是用户确认的既定决定（"后面的没有打错字"）；index%3 分区里的批次 3 书池当前没有专属定时窗口。

关键不变量（违反任何一条都会复发旧事故）：

1. **提示词零状态、纯参数**——动态状态全部在文件里，由 MCP 工具读写。
2. **一书一主**——一个 worker 进程同一时刻只持一本书；他者新鲜锁不可抢，自己的锁随便进。
3. **停止条件不可自评**——合法停止原因只有"书池已空 / 容量收尾 / 系统终止"三种，其余一律重派。
4. **单一写者**——Windows 端 git 只 add `翻译项目` 与 `mcp`；根看板（Plan.md / README / 根 CSV）由 Mac 端独占刷新。

## 二、提示词分层设计（为什么长这样）

提示词分三层，每层职责严格分离：

### 2.1 worker 指令块（嵌入子代理的无状态循环）

`batch_begin → claim → context_pack → get_blocks → 直译 → submit` 每章循环；PASS 进下一章、PARTIAL 补块重交、FAIL 修复重交（幂等）、同一章 3 次未过跳过换篇。

- **"本指令即全部流程"**：worker 不读任何文档，防止即兴发挥（含改代码，见 §4.8）。
- **运行纪律条是 v3 的核心**（成因见 §4.3）：明确告诉 worker "额度耗尽/内容拦截会由系统直接杀死回合，不需要也不允许你自行判断该收尾了"，并点名禁止三类借口（完成一本书 / 运行时间较长 / 完成一定章数）。只留两个合法自主返回：
  - ① 候选与重试队列均空 → 总结注明"书池已空"；
  - ② 上下文明显过重 → 总结注明"容量收尾需重派"并给出当前书名（worker 上下文一次性，跑久了确实需要换血，这是唯一无法从外部判定的条件）。
- **禁止 worker 碰 git 和 refresh_progress.py**：收尾统一在调度会话执行，避免并发提交竞争。

### 2.2 槽位管理层（调度会话职责）

- **保持并发度 2**：收到 worker 完成通知先查停止原因，不是三种合法原因（提前收尾）→ 按原指令立即重派补位。
- **容量收尾的特殊处理**：先 `rm "翻译项目/<书名>/认领.md"` 再重派——否则该书 4 小时活跃锁会拦住新 worker，断点卡死到锁过期。锁删了也不怕双写：CSV 的 doing 状态 + 块级断点让新 worker 从剩余块续译。
- **死亡分诊协议**（worker 报错死亡而非总结时）：
  - **额度类**（429 / 额度不足 / quota / insufficient）→ **不拉黑任何书**，直接结束本窗口。额度约 5 小时后重置，下个窗口 `batch_begin` 自动续跑断点。
  - **拦截类**（1301 / 敏感内容）→ 从报错文本找书名，找不到 `tail -1 mcp/活动日志.txt` 取最近的书 → 追加到 `mcp/拦截清单.txt` → 立即重派补位；**累计拉黑 3 本才关闭该槽位**。
  - 分诊错误是最伤的：把额度死当拦截死会冤枉好书（白拉黑 48h+），把拦截死当额度死会让下一个 worker 在同一本书上再死一次。

### 2.3 git 层（开局同步 + 收尾提交，单一写者）

**开局自理 + 同步**（v4.3/v4.4）：派工前两步——① 工作区若有 `翻译项目/` 或 `mcp/` 的未提交改动（上个窗口被额度杀死、收尾 git 没执行——10-24 三窗口 153 文件滞留实证），先 `git add 翻译项目 mcp && git commit -m "sync: 上窗口残留入库"`；② `git -c http.proxy=... pull --rebase -X ours origin main` 拉取 Mac 端进度（不拉取会在旧 CSV 上重译已完成章节——数据不丢但 token 白烧）。两步失败都不阻塞派工。

**收尾提交**：

```
git add 翻译项目 mcp && git commit -m "sync: 批次N MCP 自动翻译"
→ git -c http.proxy=http://127.0.0.1:7890 pull --rebase -X ours origin main
→ git -c http.proxy=http://127.0.0.1:7890 push
```

- git 任一步**失败一次即止**，不重试不强行推。
- **不运行 refresh_progress.py，不 add 仓库根目录任何文件**：根看板是派生文件、由 Mac 端（审核侧）独占刷新。两侧提交集不相交后，rebase 恒为 fast-forward，冲突面归零（成因见 §4.5）。

## 三、状态模型与并发机制

状态只存在于文件。每类文件的语义与保护机制：

| 文件 | 语义 | 保护机制 |
| :--- | :--- | :--- |
| `翻译项目/<书>/translation_queue.csv` | file, size_kb, status(todo/doing/done)，唯一事实源 | 跨进程文件锁；doing 残留由 batch_begin 块级回收 |
| `翻译项目/<书>/认领.md` | 书级锁，48h TTL | 持有者身份 + 心跳 + 4h 活跃宽限（见下） |
| `mcp/拦截清单.txt` | 1301 回避书目，一行一个 | 三层防线 + 跨窗口持久（见下） |
| `mcp/活动日志.txt` | 工具足迹 `ts\|tool\|project\|file`，append-only | gitignored；死亡归因的证据源 |

### 3.1 认领锁与"一书一主"

- 持有者写入格式 `translate-mcp <hex8>`，`<hex8>` 是 MCP 服务器进程的 `_SELF_ID`（uuid 前 8 位）。**每个会话各有一个服务器进程**，所以 _SELF_ID 就是 worker 的进程身份。
- **心跳**：claim_task 与 submit_translation 都会刷新锁时间戳。锁龄从最后一次工具调用算起。
- **三种拦截规则**：
  - 外部锁（持有者不是 translate-mcp，如 Mac 审核）：未超 48h 不可接管；
  - 他人的 MCP 新鲜锁（锁龄 < 4h 且非自己）：拒绝——一书一主，防两个槽位换着派书互相踩；
  - 自己的锁（`_holder_self`）：无条件放行——这是蛇形事故的修复点（§4.2）。
- 锁的回收：全书 todo 清零自动删锁；batch_begin 回收时清 MCP 幽灵锁；"容量收尾"由调度会话手动 rm。

### 3.2 拦截清单（1301 三层防线 + 跨窗口持久）

1. **worker 层**：遇 1301 跳过该书、记书名、继续下一本（尽力而为，worker 可能直接死）；
2. **调度会话层**：死亡分诊为拦截类 → 书名追加到拦截清单 → 重派；
3. **服务器层**：`batch_begin` 把清单内书目从候选池与重试队列排除，`claim_task` 直接拒绝认领——**这保证跨窗口不重复拉黑**（窗口 A 拉黑的书，窗口 B 的 worker 根本碰不到）。

解冻 = 人工删除该行（Mac 审核确认无害后）。当前在列：`edgar-wallace_terror-keep`、`georgette-heyer_beauvallet`。

### 3.3 batch_begin 的回收语义（块级断点）

每个窗口开始时对 doing 残留逐章判定：全部块已译且过校验 → 回填 done；部分块已译 → 保留盘上译文、进重试队列置顶（"断点:已译 n/N 块"）；无可复用 → 整章重投。这使得**任何时刻的死亡都是无损的**——下一窗口自动续译。

## 四、踩坑实录（按教训价值排序）

格式：现象 → 根因 → 修复 → 铁律。

### 4.1 毒会话（PM1800 v1）

- **现象**：任务创建后首跑正常，之后每次 firing 都在处理输入阶段 1301，窗口完全空转；换提示词无效。
- **根因**：内容审核按**整个会话历史**判定。历史里一旦进入被标记内容，之后每一轮都带毒。
- **修复**：删除任务，在**全新对话**中重建（现 11feab52）。
- **铁律**：①绑定会话里绝不手动跑翻译、绝不粘贴原文；②翻译任务一律在全新对话中创建（Cron 任务绑定创建会话， firings 注入同一会话）；③会话反复 1301 且报错无书名线索 → 判毒会话，删任务重建，别修提示词。

### 4.2 自锁蛇形（最严重的一次）

- **现象**：加"一书一主"后，某夜 02:10–03:23 产生 111 次 claim，蛇形穿越约 25 本书、每本只译 1 章，无一本书连续两章。
- **根因**：所有 MCP worker 的锁持有者字符串相同（"translate-mcp"），"拒绝他者新鲜锁"把 worker **自己的锁**也拦了——它认领第 2 章时被第 1 章留下的锁挡住，只好换书。
- **修复**：`_SELF_ID` 每进程唯一 + `_holder_self()` 放行自己。验证三 case：他人新鲜锁拒绝 ✓、旧格式锁拒绝 ✓、自己的锁重入 ✓。
- **铁律**：互斥的"他者判定"必须基于**身份**而非**类别**；改并发规则后必须验证"同一 worker 连续两章"这个最小闭环，书级交替（蛇形）就是此 bug 的指纹。

### 4.3 提前自主收尾

- **现象**：PM2105 / AM0715 译完一本书就返回总结，额度还剩很多。
- **根因**：v2 提示词写了"额度耗尽→停止"。但真实的额度死亡是**系统杀回合**，worker 根本执行不到自己的"停止"指令——所以任何写给 worker 的停止条件都只会被**提前**触发，成为借口。
- **修复**：v3 运行纪律（§2.1）：明说系统会杀回合、禁止自评收尾、只留两个合法自主返回；调度会话对一切提前收尾原指令重派。
- **铁律**：给 AI 的停止条件必须**不可自评**；能自评的条件一定会被提前满足。用户对此有明确要求："每个窗口都跑完额度为止"。

### 4.4 [1301] 内容拦截（"额度充足却 2 分钟暴毙"）

- **现象**：2:10 窗口额度充足，只跑了 2 分钟就死。同书同章可稳定复现（terror-keep 10-viii 连死 3 次）。
- **根因**：API 级内容审核杀整个回合（`turn.failed` 于 processing_input 或生成阶段），与额度无关。特定书的敏感段落（暴力等）是稳定触发器。
- **修复**：三层防线 + 跨窗口持久拉黑 + claim 服务端拒绝（§3.2）。
- **铁律**：暴毙归因先看 app 日志的 turn.failed 错误码再下结论；"额度充足却死"≠额度问题。分诊结果直接决定拉黑与否，错了要么冤书要么连锁死亡。

### 4.5 收尾 push 失败（一夜 155 章 submit 未提交）

- **现象**：某夜全部译文滞留工作区未推远端。
- **根因**：Mac 端自动提交看板 → 远端领先 → worker 的 push non-fast-forward；"失败一次即止"让它直接放弃，且无人补推。
- **修复**：链中加 `pull --rebase`；v4.2 进一步做**单一写者**——Windows 只 add `翻译项目 + mcp`、不碰根看板，Mac 独占 Plan.md/README/根 CSV。两侧提交集不相交 → rebase 恒 fast-forward。**根本认识**：翻译与审核的产出本是纯新增文件，冲突全部来自两侧共同重建的派生看板；派生文件必须单一写者。
- **铁律**：多方共写一个仓库时，先划清每个文件的**唯一写者**；提交集不相交比"更聪明的合并策略"可靠。

### 4.6 分块器失效（10 万字符巨块）

- **现象**：ii-2 章节分出 4 块，第 1 块 100,477 字符，worker 翻译超限死亡。
- **根因**：该章段落只用单个 `\n` 连接、无空行，"按空行打包"失效。
- **修复**：`_shatter()` 句级兜底（句末标点正则切句、贪心装包 ≤2,400、超长单句硬切）。实测 109,329 字符 → 48 块、最大 2,399。
- **铁律**：对"结构可能缺失"的文本必须有句级兜底；块上限是生死线，不是优化项。

### 4.7 幽灵锁（51 把锁挡住候选池）

- **现象**：被系统杀死的 worker 留下认领锁，48h TTL 内把大批候选书挡在池外，一度手工清理 51 把。
- **修复**：batch_begin 回收时自动清 MCP 幽灵锁；全书完成自动删锁。
- **铁律**：锁必须有与持有者生命周期挂钩的回收路径，只靠 TTL 会积累垃圾。

### 4.8 worker 即兴改代码

- **现象**：10-23 02:18 某 worker 遇到障碍没有按指令跳过，而是直接对 `translate_mcp.py` 做了手术（补丁恰好正确，已保留）。
- **风险**：下次未必正确；且运行中改服务器代码会污染 git 与现场。
- **现行缓解**：worker 指令首行"本指令即全部流程"。**待决**：工具受限的自定义 agent 类型（禁 Write/Edit/Bash）。

### 4.9 额度死亡带走收尾（隔夜 153 文件滞留）

- **现象**：10-24 晚 18:00 / 21:05 / 10-25 02:10 三窗口共产出 119 章，全部滞留工作区未提交——git 里看不到任何 sync 提交。
- **根因**：额度耗尽连调度会话一起杀死，收尾 git 无从执行；即使 worker 先死、调度会话活着，"额度类→直接结束本窗口"也不会触发收尾（收尾条件是两槽位合法停止）。
- **修复**：v4.4 开局自理——每个窗口开局先提交上窗口残留再 pull，跨窗口自愈闭环。
- **铁律**：审计时工作区脏 ≠ 事故，先看是不是"额度死亡的正常滞留"；但超过一个窗口周期没人收就是问题了。

### 4.10 僵尸 MCP 服务器（07:15 窗口"零活动"假象）

- **现象**：07:15 窗口连续两天在活动日志里零条目，一度被误判为"额度重置错位、没跑起来"。实际 app 日志显示 worker 每天都在正常调工具（10-24 晨 82 claim/87 submit、10-25 晨 49 claim/50 submit），10-25 晨还完成了两本书（banjo 29/29、indian-summer 24/24）。
- **根因**：MCP 服务器进程**随绑定会话常驻**。bc5a15a5 绑定的会话创建于 10-22，其服务器进程加载的是 10-23 全部补丁**之前**的 translate_mcp.py——没有活动日志、没有 _SELF_ID 一书一主、没有 1301 拉黑防线、没有 2.4KB 分块兜底（巨块把预算 52~65 分钟烧光，[1308] 提前死）。
- **指纹**：认领锁持有者为旧格式 `translate-mcp`（无 hex8 后缀）＝旧代码服务器在跑；"活动日志零条目但 app 日志有 tool.call"也是指纹。
- **修复**：删除该自动化，在**全新对话**中用当前模板重建（新会话＝新服务器进程＝当前代码）。审计会话绝不能代建——Cron 绑定创建会话，会把每日注入绑到审计会话上。
- **铁律**：改了 translate_mcp.py 之后，逐个窗口核对锁格式指纹；"活动日志零活动"必须先查 app 日志的 tool.call 再下结论。

### 4.11 归因错误的教训（审计者自身）

- 我犯过的错：把无关自动化 6d88a8c4 当成重复翻译任务（实为用户的新闻简报任务）；把拦截清单里的 terror-keep / beauvallet 当终态（Mac 审核可能会解冻它们）。
- **铁律**：看到"异常"的自动化或状态变更，先假设**用户侧或远端（Mac）的人为因素**，再怀疑系统故障；不在自己知识范围内的任务 ID 不下结论。

## 五、运行数据与规律（截至 2026-10-24）

### token 经济学

| 口径 | 数值 |
| :--- | :--- |
| 旧长会话流程 | 每轮 ~350K 历史重载税（会话历史越长越贵，不可持续） |
| MCP 工具流 | ~93K tokens/章（约 4× 降） |
| worker | ~25K tokens/章 |
| 调度会话 | ~3.5K tokens/firing（瘦分发器的意义） |
| worker 单次运行 | 上下文一次性，最高 ~570K 后丢弃（设计如此，用完即弃） |

cache 行为：窗口间隔后的首轮 cache-miss 属正常，不要误判为异常消耗。

### 速度与并发

单 worker ~1.5 分钟/章是**生成速度硬瓶颈**（已到顶），窗口时间有富余——所以 v4 用双 worker 并行直接翻倍吞吐。并发的正确性完全靠锁机制（§3.1），不靠调度会话的簿记。

### 额度窗口

- 额度窗口从**首次消耗**起算 **5 小时**（不是从耗尽起算）。额度耗尽报 `[1308] 已达到 5 小时的使用上限`，**报文自带精确重置时间**（排障第一手证据：重置时间 − 5h = 窗口首耗时刻）。4 个窗口（18:00 / 21:05 / 02:10 / 07:15）按 ~5h 间隔排布，即"上一窗口首耗 + 5h ≈ 下一窗口点火"。
- **手动重置卡**：用户会手动重置后继续推进；若重置卡使用失误，下一个窗口可能**开局零额度秒死**——这是已知的良性失败（额度类死亡、不拉黑、下窗口自动续跑），审计时不要当成事故。

### 远端 MacBook（审核侧）

- 运行翻译后的**校对审核**，会更新进度文件、独占刷新根看板（Plan.md 全量重写 + README + 根 CSV + 审核报告文件）。
- 因此审计时看到根看板变化、或拦截清单/进度被改动，先想 Mac，再想异常。

## 六、排查手册（跑批审计 SOP）

### 6.1 数据源

| 数据 | 路径 | 用途 |
| :--- | :--- | :--- |
| 活动日志 | `mcp/活动日志.txt` | 工具足迹 `ts\|tool\|project\|file`；双 worker 与蛇形的判定依据 |
| 拦截清单 | `mcp/拦截清单.txt` | 拉黑史；比对死亡分诊是否正确 |
| git 历史 | `git log --stat` | sync commit 范围应只有 `翻译项目/`+`mcp/`；rebase 应无冲突 |
| app 日志 | `~/.zcode/cli/log/zcode-YYYY-MM-DD.jsonl` | **UTC 时间戳（本地 = UTC+8）**；turn.failed 事件定位死因 |
| 模型 IO 日志 | `~/.zcode/cli/rollout/model-io-*.jsonl` | usage（inputTokens/outputTokens/cacheReadTokens）；**只保留约 3 个文件，事后审计要趁早** |
| 项目 CSV | `翻译项目/<书>/translation_queue.csv` | done/doing/todo 分布、断点位置 |

### 6.2 双 worker 正常的证据形态

活动日志里**两本书各自连续多章、相互交替**。反例指纹：

- 一本书连续多章、另一边没有 → 单 worker（旧故障"只开了一个子代理"）；
- 二十几本书各 1 章 → 蛇形复发（§4.2），立即查 `_SELF_ID` 逻辑是否被改动；
- 认领锁持有者无 hex8（旧格式 `translate-mcp`）→ 僵尸服务器在跑旧代码（§4.10）。

### 6.3 死亡归因流程

1. app 日志找 `turn.failed` 事件，看错误码：429/额度类 vs 1301/拦截类；
2. 拦截类 → 活动日志 `tail` 定位最近的书名 → 核对该书**是否已在拦截清单**（在 = 窗口 A 已拉黑、窗口 B 不应再死一次；不在 = 需补拉黑）；
3. 额度类 → 确认**没有**书被误拉黑；
4. 处理输入阶段即死且无书名线索、反复发生 → 毒会话（§4.1），删任务重建。

### 6.4 单窗口验收清单

1. 两槽位各持一书、连续 ≥2 章（双 worker + 一书一主）；
2. sync commit 只含 `翻译项目/` 与 `mcp/`（单一写者）；
3. push 纯 fast-forward、零冲突；
4. 死亡分诊正确：额度死→未拉黑；拦截死→已拉黑且跨窗口生效；
5. 两槽位均到达合法停止原因（书池已空 / 容量收尾 / 系统终止）。

## 七、已知风险与接受的权衡

- **>4h 无 submit 的超大章**：理论上锁过期后可被另一 worker 抢走，造成短暂双写。接受——submit 幂等覆盖，后果轻微。
- **worker 即兴行为**（含改代码）未根除，靠指令约束 + git 可回滚兜底；根治待工具受限 agent 类型。
- **正本漂移**：提示词改动必须**同时**改模板文件与线上任务（CronUpdate），只改一处必然漂移。
- **rollout 日志滚动**：仅留 ~3 个文件，token 审计必须在文件还在时做。
- **额度重置卡误操作** → 下窗口空转：已知良性，无需修复。
